`test/auth/` の単体テスト（`safeRedirectPath` のオープンリダイレクト対策、`isAdminById` の管理者判定）は、
単なる品質担保ではなく **セキュリティ回帰の検出装置**として位置づけられている（CLAUDE.md の `/goal`「証拠＋抜け道封じ」・
`specs/sprint-contract.md` の Generator-Evaluator で「テストが通ること」が完了の証拠に使われる）。

**Why:** 証拠として使われるテストが弱い（攻撃ベクタの網羅漏れ、認可キーを検証しないスタブ）と、
実装側の認可・リダイレクト検証が退行しても「全通過」という証拠だけが残り、制御が効いているように見える。
制御の実効性そのものが劣化するため、テスト差分はセキュリティ観点の対象に含まれる。

**How to apply:** `test/` 配下が差分に出たら、(1) 攻撃ベクタの網羅（実装の各拒否分岐に対応するケースがあるか）、
(2) スタブ・モックが「どのテーブル / どのカラム / どの値で絞ったか」を検証しているか、
(3) 失敗時に fail-closed になることを固定するケースがあるか、を確認する。
テスト対象の純関数の呼び出し元（`app/auth/**` の `redirect()` / `NextResponse.redirect()` 等）まで辿り、
テストが前提としている不変条件が実際の消費側で保たれているかも併せて見る。
既知のアプリ側リスクは [[open-risks]] を参照。
