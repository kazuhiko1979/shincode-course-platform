`npm test`（Node 組み込み `node:test`、外部依存ゼロ）は **開発／CI 時のみ動く検証系**であり、アプリのランタイム性能・本番バンドルには一切影響しない。2026-07-31 実測の受容済み前提：

- 全体：wall 0.44–0.50s（ウォーム）／0.98s（コールド）、ピーク RSS ~122MB（親＋子プロセス）、11 テスト。
- `node --test` は **テストファイル1本＝1子プロセス**。テストが `lib/` 経由で `next/*` や `@supabase/ssr` を含むモジュールグラフを読む場合、1プロセスあたり ~160ms の固定ロードコストが乗る（依存なしモジュールは ~68ms）。この固定コストはファイル数に比例する。
- `.ts` を type stripping で直接実行するため Node の `MODULE_TYPELESS_PACKAGE_JSON` 再パースコストが乗る（Node 自身が「performance overhead」と警告する）。現規模では総時間 ~350ms に埋もれる水準。
- tsconfig の `include: **/*.ts` によりテストファイルは `tsc` のプログラムに入る（`npm run typecheck` / `next build` の型チェック対象）。747 ファイル中2ファイル・下流依存なしの葉ファイルのため増分型チェックへの波及なし。`.mjs` は include 対象外で型チェックコストゼロ。

**Why:** テスト実行コストは「作業時のみ」かつ実測で 1 秒未満・ビルド（数十秒）比で無視可能。ユーザー価値（回帰検出）が上回るため、マイクロ最適化の対象としない判断（[[hook-overhead]] と同じ扱い）。
**How to apply:** テスト実行時間・テストプロセスのメモリ・型チェックへのテストファイル混入を、これ以上ボトルネックとして再指摘しない。再評価するのは (a) テストファイルが数十本規模に増えて1本あたりの固定コストが体感化したとき、(b) テスト用の仕組みがアプリのランタイム経路（NODE_OPTIONS 常時登録・`app/`・`lib/` からの参照など）に漏れたとき のみ。
