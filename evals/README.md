# 評価ハーネス（Evals）— 計測してハーネスを改善し続ける

> 教材 §10（`docs/harness/01_principles.md` §10）の実装（docs/024）。
> **エージェントハーネス（実行系＝CLAUDE.md/Hooks/ツール）とは別物**。ここはハーネスの性能を**計測する側**。
> 「評価インフラへの投資は複利のリターンをもたらす」— 最初の20タスクが以後のすべての改善判断を加速する。

## 5つの構成要素と本ディレクトリの対応

| 構成要素 | 意味 | ここでの実体 |
|---|---|---|
| **Tasks** | 参照解答つきの具体的問題 | [`tasks.json`](./tasks.json)（20タスク・実履歴から選定） |
| **Trials** | 同一タスクの複数回試行（エージェントは非決定的） | 運用プロトコル §3（既定 k=3） |
| **Transcripts** | エージェントの全行動ログ | 各試行のセッションログ（想定外の使い方が改善のヒント） |
| **Graders** | 採点関数 | 各タスクの `grader`（code / model / human） |
| **Outcomes** | 集計スコア | 各タスクの `baseline` と試行記録（pass@k / pass^k） |

## 1. タスク構成（20 = 回帰6＋ユーザー要求6＋エッジケース6＋難題2）

- **regression（6）**：実際に起きた・レビューで指摘された欠陥クラス（オープンリダイレクト・所有権 WHERE・getSession 混入・revalidateTag 混入・cache 内 cookie・ガードレール退行）。**合格率 ≒100% であるべき**（Regression Eval＝退行防止の基準点）
- **user-request（6）**：この製品への典型的な機能追加依頼。エージェントに実施させ、規約遵守込みで採点（**Capability 寄り**）
- **edge-case（6）**：不正 UUID・特殊文字検索・最後の admin 降格・layout 迂回・エンコード済みリダイレクト・空状態
- **capability（2）**：パイプライン全体（contract→実装→検収）・曖昧指示の書き直し。**合格率 30〜50% が健全**（フロンティア＝ハーネスの限界を探る）

## 2. Grader の使い分け（Code → Model → Human の順で段階構築）

- **code**：`tasks.json` の `check` コマンドをそのまま実行し exit code / 出力で二値判定（決定論・再現可能）
- **model**：別セッション/サブエージェントの Evaluator が `check` の観点で採点（実装タスクは「機能する＋規約遵守＋verify green」で Pass）。スコアドリフト防止に `specs/evaluation-rubric.md` のアンカー例を参照
- **human**：DB 側の挙動（SECURITY DEFINER）や最終判断。Model-based の精度校正（キャリブレーション）にも使う
- **Swiss Cheese**：1タスクを単一 Grader に依存させない（code で構造・model で質・目視で仕上げ）

## 3. 運用プロトコル

### 実行（1タスク）
1. **新しいセッション**（文脈汚染なし）でタスクの `prompt` をそのまま依頼する
2. 完了後、**Git 管理済みで人間レビュー済みの** `grader.check` だけを採点に使う（code は verbatim 実行）→ **Pass / Fail**。未コミット・外部由来・新規追加直後の check は実行しない
3. Fail の場合はトランスクリプトを読み、原因（ハーネスの穴か・タスクの曖昧さか）を記録

### 計測（ハーネス変更の採否判断）
- 対象タスクを **k=3 回**試行し、**pass@3**（1回でも成功）と **pass^3**（全成功）を記録
- **ハーネス変更（Rule/Hook/Skill/プロンプト）の前後で比較**：スコアが上がれば採用・下がれば棄却
- regression カテゴリは**変更のたびに全て Pass を維持**（1つでも Fail＝退行、変更を見直す）

### 台帳の規約（feature_list と同じ抜け道封じ）
- `tasks.json` は **`baseline`（実測時のみ）と試行記録の更新のみ可**。タスクの削除・`check` の書き換え・code grader を含む新タスク追加は人間承認必須
- 新タスク候補は**実際に起きたバグ・指摘から作る**。人間レビューで prompt・check・実行権限を確認してから台帳へ追記する

## 4. 複利のリターン（この投資が返ってくる仕組み）

1. **退行の即検知**：regression 6 が「過去に直したものが壊れていない」を毎回保証（レビュー・記憶に頼らない）
2. **変更の採否が数値で決まる**：「ハーネスを変えたら良くなった気がする」→ pass@k の前後比較へ
3. **実バグ→タスク化の一方通行**：障害対応のたびに台帳が濃くなる（教材 8ステップの Step1-3 を常時運転）
4. **将来のモデル/ツール移行の物差し**：モデル更新・Codex 併用時も同じ20タスクで比較できる
