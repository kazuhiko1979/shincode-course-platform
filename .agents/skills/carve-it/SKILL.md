# Carve It

## 目的

変更を「技術レイヤー」ではなく、利用者価値または検証可能な振る舞いの単位で薄切りにする。各スライスは、前のスライスを積み上げた状態で、意味が説明でき、対象テストを実行でき、レビュアーが短時間で判断できる状態にする。

## 発動判断

次のいずれかに該当したら、実装やレビューの開始時に carve-it を適用する。

- ユーザーが薄切り、小さなコミット、レビュー単位への分割、carve-it を明示した。
- `git diff --stat` の変更行数が約300行以上、変更ファイルが約8個以上になった。
- DB/契約/API/ロジック/UI/テスト/ドキュメントなど、複数レイヤーまたは複数の独立した関心事を同時に変更する。
- 1コミットの説明が一文で表せない、またはレビュアーが複数の仮説を同時に追う必要がある。

閾値は機械的な強制ではない。小さくても依存関係が強い変更は一つに保ち、生成物・ロックファイル・単一マイグレーションなど分割すると壊れるものは関連するスライスに含める。

## 手順

### 1. 現状を固定する

最初に `pwd`、`git status --short`、現在のブランチ、比較対象（通常は分岐元または直近の安定コミット）、`git diff --stat`、既存の `AGENTS.md`・Rules・テスト手順を確認する。ユーザーの既存変更や未追跡ファイルを、今回のスライスに勝手に混ぜない。公開済みコミットの履歴を書き換えない。

変更が未コミットなら、最初に「変更前提」「スライス一覧」「各スライスの検証」を短く提示する。コミットを求められていない場合は、論理的な実装単位を保ち、コミット作成は行わず、推奨するコミット境界だけを報告する。

### 2. スライスを設計する

依存関係を確認し、最小の動作する順に並べる。通常は次の順序を検討する。

1. 仕様・型・契約など、後続の基準になる変更
2. データ層・マイグレーション・サーバー側の最小実装
3. 利用者向けの一つの振る舞い（UI/API）
4. その振る舞いのテスト、エラー処理、観測性
5. ドキュメント・運用・補助的な整理

各スライスについて、目的、含めるファイル、前のスライスへの依存、実行する検証、完了条件、コミットメッセージ案を明記する。一つのスライスに複数の無関係な目的を入れない。目安は「一つのレビュアー質問に答えられる」大きさで、行数を小さくすること自体より、単独で意図と検証結果を説明できることを優先する。

### 3. 実装・コミットする

ユーザーがコミット作成を依頼している場合、スライスごとに次を繰り返す。

1. そのスライスだけを編集・ステージする。混在したファイルは `git add -p` などでハンク単位に分ける。
2. 対象テスト、lint、型チェック、`git diff --check` を実行する。
3. 検証が通ったスライスだけを、目的が一つの命令形または Conventional Commit でコミットする。
4. `git show --stat --oneline HEAD` と次のスライスの差分を確認する。

既存の一つのローカルコミットを分割する場合は、未公開であることと書き換え許可を確認してから `git rebase -i` 等を使う。公開済みなら履歴を改変せず、後続の補正コミットまたは新しいレビュー用ブランチを提案する。作業ツリーにユーザー変更が混在している場合は、先に退避・分離方法を示し、推測で `reset` や破棄をしない。

### 4. スライス単位でレビューする

各コミットを親コミットとの差分として個別にレビューし、レビュー順序、目的、検証結果、未解決の依存関係を記録する。最終的に全スライスを積み上げた状態でフル検証を一度実行する。テストが失敗した場合、そのスライスを細分化するか、失敗理由をコミット前に解消する。

## 出力形式

作業開始時は次の形式で簡潔に示す。

```text
Carve plan:
1. [目的] — [対象ファイル] — [検証]
2. [目的] — [対象ファイル] — [検証]
順序の理由: [依存関係]
コミット: [作成する / 作成しない]
```

完了時は、スライスごとのコミットまたは推奨境界、実行した検証、残ったリスクを報告する。分割によってテスト不能な中間状態が生じる場合は、その理由を明記し、無理に分割しない。
