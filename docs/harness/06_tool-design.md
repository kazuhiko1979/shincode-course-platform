# エージェント向けツール設計（ACI 基準と監査台帳）

> 教材 §8（[01_principles.md](./01_principles.md) §8「プロンプトよりツール設計が重要」）を本プロジェクトの**運用基準**に落としたもの。
> 「ツール」＝エージェントが知覚するアフォーダンス全部：**MCP ツール・npm scripts・スラッシュコマンド/スキル・フック・サブエージェントの tools 定義**。
> 基準：**初めて使うジュニア開発者でも迷わないか。**

## 2. 選択的実装（タスク指向で3〜5に絞る）

- **原則**：「このツールが無くてもタスクを完了できるか？ → Yes なら足さない」。全 API をラップしない勇気（Vercel は80%削減で成果向上）。
- **MCP サーバーの追加基準**：docs/ チケットに対応する具体的タスクが必要とする時だけ有効化。**使用実績が無くなったサーバーは無効化**する。
  - 👉 **推奨アクション**：`notion` は本プロジェクトで使用実績なし。`.claude/settings.local.json` の `enabledMcpjsonServers` から外す（個人設定のため人間が実施）。
- **サブエージェントの新設基準**：既存の tools 継承で足りるなら専用定義を作らない。作る場合は **5ツール以内**から始める（reviewers が手本）。
- **npm scripts の追加基準**：エージェントの1タスクに対応する動詞（`verify` のような統合コマンド）を優先し、部分コマンドの乱立を避ける。

## 3. コンテキスト効率（返す情報を最小に）

- ツール/スクリプトの出力は**アクションに関係する情報のみ**。内部ID・冗長ログを垂れ流さない。
  - 実例：`session-start.sh` は 60行/300字/制御文字の三段ガード付きで注入。レビュアーは要約（1〜2k トークン）で返し詳細はファイルへ（05_playbook §計画のメモリ保存）。
- 長い出力が必要な検証（build ログ等）は `grep`/`tail` で要点だけ提示する（完了報告の証拠は結論行＋exit code）。
- CLAUDE.md には**判定表・手順の要約だけ**を置き、詳細はリンク先へ（Select 戦略。1回の追記で +20% を超えたら分離を検討）。

## 4. 命名戦略

- **`{対象}_{操作}` / 動詞始まりのタスク名**で、名前だけで対象と操作が分かること（教材の `{service}_{resource}_{action}` 3層の簡約）。
  - 良い実例：`validate-bash.sh`・`lint-on-save.sh`・`session-start.sh`（いつ何をするかが名前で分かる）／`npm run verify`（タスクそのもの）
  - 悪い例：`check.sh`・`run.sh`・`util.sh`（何の check か分からない＝毎回説明文を読ませる）
- スラッシュコマンドは**ユーザーの意図の言葉**で（`/push-review`＝「レビューして push したい」）。
- 将来カスタム MCP を作る場合は `{service}_{resource}_{action}`（例：`course_videos_search`）を正典とする。

## 5. エラー設計（自律回復を促す）

すべての agent-facing エラーは **①何が起きたか ②なぜダメか ③次に何をすべきか（代替案）** を含める。「ジュニア開発者へのドキュメント」の粒度。

- 実例（validate-bash.sh）：`BLOCKED: 一括ステージ（-A/--all/.）は禁止。変更パスを明示してください。`（理由＋代替）
- 実例（validate-supabase-write.sh）：ブロック理由＋「人間の承認を得たうえで CLAUDE_ALLOW_DB_WRITE=1」（回復手順の提示）
- アンチパターン：`400 Bad Request`・`エラーが発生しました` だけを返す（エージェントが次の一手を推測できない）。
- 新しいフック・スクリプトを書くときはこの3点セットをレビュー基準にする（reviewers が確認）。

## 6. 3フェーズ改善ループ（作りっぱなしにしない）

| フェーズ | 内容 | 本プロジェクトでの実施方法 |
|---|---|---|
| ① プロトタイプ | LLM フレンドリーな説明付きで作る | 名前（§4）＋エラー3点セット（§5）＋最小ツール（§2）で実装 |
| ② 評価 | 現実的なシナリオでテスト | **pipe テスト**（フックは JSON を流して exit code 検証。#018 の 46/46 が手本）＋ `npm run verify` |
| ③ 協働改善 | **トランスクリプトを読んで**想定外の使われ方を観察→改善 | セッションでの誤発火・自己ブロック・迂回を見つけたら docs/ に記録して調整（実例：#018 で「危険文字列を含むだけのコマンドが自己ブロックされる」を観察→`git commit -F` 運用と既知の挙動を文書化） |

> ツール変更も**仮説**（01_principles §11）：「エージェントが X を誤用するはず」→ 構造で補助 → トランスクリプトで検証 → 外れたら取り除く。

## 運用チェックリスト（ツールを足す/変える前に）

- [ ] 無くてもタスクを完了できるか？（Yes なら足さない）
- [ ] 名前だけで対象と操作が分かるか？
- [ ] 出力はアクションに必要な情報だけか？
- [ ] エラーは「何が・なぜ・次にどうする」の3点セットか？
- [ ] pipe テスト等の現実的シナリオで評価したか？
- [ ] 導入後、トランスクリプトで想定外の使われ方を観察したか？
