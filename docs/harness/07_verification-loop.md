# 検証ループ（3戦略のルーティングと検証の階段）

> 教材 §9（[01_principles.md](./01_principles.md) §9「フィードバックループという構造そのものが品質を2〜3倍改善する」）の運用ルール。
> **原則：まずルールベースで始め、ルールで表現できない基準がある場合のみ他の戦略を追加する。**
> **追加原則：過剰な検証を避け（変更に比例させる）、シンプルなルールから複雑なルールへ。**

## 1. 3戦略と本リポジトリの実物

| 戦略 | 性質 | 得意 | 本リポジトリの実物 |
|---|---|---|---|
| **ルールベース**（常にベースライン） | 決定論的・高速・曖昧さゼロ | 構文・型・テスト・規約違反 | `npm run verify`（lint→typecheck→test→build）／CI／PostToolUse lint-on-save（編集直後）／PreToolUse ガード（実行前）／フックの pipe テスト |
| **ビジュアル** | スクショ×マルチモーダル評価 | レイアウト崩れ・余白・階層・両テーマ | Playwright MCP でスクショ → 目視/評価（`specs/evaluation-rubric.md` の軸で見る） |
| **LLM-as-Judge** | 独立した文脈で主観品質を採点 | 可読性・UX・一貫性・セキュリティ設計 | `/push-review`（3レビュアー投票）／Evaluator 検収（`specs/sprint-contract.md` 全項目 Pass）／rubric 採点（6軸×重み） |

## 2. 検証の階段（変更の種類 → 必要十分な検証）

**過剰な検証を避ける**：下表の「必須」だけで足りる変更に、上位の戦略を持ち出さない。

| 変更の種類 | 必須（ルールベース中心） | 条件付きで追加 |
|---|---|---|
| docs/md のみ | リンク・数値整合の確認（横断する数値は列和を再計算）。※ランタイム無変更なら `verify` は任意（AGENTS.md §4 の義務は**コード・設定の変更時**） | — |
| 純ロジック（`lib/`・`test/`） | `npm test`＋`npm run verify` | — |
| UI の小修正 | `verify`＋`npm run dev` 目視（lint-on-save は編集時に自動） | レイアウトに触れたら両テーマ・主要幅のスクショ確認（**ビジュアル**） |
| UI の新規/リデザイン | `verify`＋dev 目視 | **rubric 採点**（LLM-as-Judge・別エージェント・合格80点）＋ Playwright スクショ（**ビジュアル**） |
| Server Action / API | `verify`＋実フォーム送信 | 認可に触れたら3ロール確認 |
| 認証・認可 | `verify`＋**3ロール確認**＋`sprint-contract.md` §2 の該当項目 | `security-reviewer` 単独起動（**LLM-as-Judge**） |
| hooks / settings / スクリプト | **人間承認**（AGENTS.md §1 変更禁止ゾーン）＋**pipe テスト**（exit code 検証）＋`verify` | — |
| push（**すべての変更・常時必須**） | **`/push-review`**（3並列・ブロッカーなしで push。`git push` 直叩き禁止） | — |

## 3. エスカレーションの判断（いつ上位戦略を足すか）

1. **ルールで表現できるか？** → できるなら**必ずルールベースに落とす**（新しい規約は lint/テスト/フックへ。LLM に決定論の仕事をさせない）。
2. **できない基準か？**（見た目の美しさ・視覚的階層・トーン・UX 動線・設計の妥当性）→ そこで初めてビジュアル／LLM-as-Judge を追加。
3. **重複させない**：同じ観点を複数戦略で検証しない（例：lint が検出できる規約違反をレビュアーにも見させるのは無駄。レビュアーはルールで表現できない観点に集中させる）。

## 4. シンプルなルールから複雑なルールへ（ルール自体の育て方）

- **新規ルールは最も単純な形で導入する**：単一の grep・単一のテストケース・1パターンのフックから始める。
- **実測で漏れ・誤検知が出たときだけ精緻化する**（推測で網羅を目指さない）。
  - 実例：`validate-bash.sh` は基本パターン配列で導入 → レビューで「ロング形式 `rm --recursive` が漏れる」と実測指摘 → パターン追加（#018）。
  - 実例：`session-start.sh` は単純な cat 注入で導入 → poisoning 懸念の指摘 → nonce 区切り・三段ガードへ精緻化（#021）。
- **ルールの複雑化にもコストがある**：誤検知（false positive）が作業を止めるなら、それは過剰な検証。緩める判断も「実測→調整」で行う。

## 5. アンチパターン（過剰な検証）

- docs/タイポ修正に 3 レビュアーや rubric 全採点を回す（コスト浪費）。
- 小さな UI 修正のたびに 6軸 rubric を全採点する（rubric は新規/リデザイン・完了前）。
- lint/型/テストで拾える違反を LLM レビューで探させる（決定論の仕事を確率に落とす逆行）。
- 同一変更に同じ検証を重複実行する（verify を2回、同観点のレビュアーを2体）。
- 最初から網羅的な正規表現・全ケーステストを書こうとする（シンプル→実測→精緻化の逆）。

> ここでの「過剰検証の回避」は**品質ゲートの省略ではない**：§2 の「必須」列は常に守る（AGENTS.md §4 検証の義務）。避けるのは「必須を超える上位戦略の乱用」。
