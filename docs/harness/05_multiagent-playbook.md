# マルチエージェント運用プレイブック（壁打ち基準＋エスカレーション）

> **基本は壁打ち（単独エージェントとの対話開発）**。プロンプトの形がパターンの発動条件を満たすときだけ、マルチエージェント設計パターンへエスカレーションして品質を高める。
> 理論は [01_principles.md](./01_principles.md) §6（単一エージェントの3つの限界／3パターン比較表）。本ファイルは**いつ・どれを・どう使うか**の運用ルール。

## 大原則（共通原則の適用）

1. **シンプルから始める** — 既定は壁打ち（単独）。エスカレーションは次のいずれかが成り立つときだけ：
   - **文脈の分離**が要る（大量トークンを消費する調査でメインの文脈を汚したくない）
   - **独立した並列性**で実時間を短縮できる（互いに依存しない作業が2つ以上）
   - **評価の独立性**が要る（自己評価バイアスの分離＝Generator-Evaluator）
   簡単な質問・小修正に大量のエージェントを使わない（**クエリの複雑さでスケール**）。
2. **各エージェントに適切なツールだけ持たせる** — ツールはアフォーダンス。多いほど誤選択が増える（ACI 原則）。下表の割り当てを守る。
3. **メモリに計画を保存する** — 委任・並列化の**前に**計画を外部ファイルへ書き出す（コンテキスト上限・セッション断絶への保険）。ワーカーの結果は要約（1〜2k トークン）でメインに返し、詳細はファイルに残す。

## パターン選択（プロンプトの形 → 発動）

| プロンプトの形（例） | パターン | 実行方法（本リポジトリの実物） |
|---|---|---|
| 質問・相談・小修正・1ファイルの変更 | **壁打ち（単独）** | メインセッションのみ。サブエージェント不要 |
| 「レビューして」「push して」「多角的に見て」 | **ファンアウト・ギャザー**（＋投票） | `/push-review`＝code/security/performance の3並列→統合判定。調査系は `Explore`/`general-purpose` を観点別に並列起動 |
| 「〜を調べて」「全部洗い出して」「横断的に分析して」 | **ファンアウト・ギャザー**（調査） | 独立した領域ごとにサブエージェントを並列。各自の結論だけ回収 |
| 機能開発（チケット・スプリント単位） | **シーケンシャルパイプライン** | ①`specs/sprint-contract.md` で完了基準を合意（Planner）→ ②実装（Generator：メイン or `serena-expert`）→ ③検収（Evaluator：別エージェントが contract 全項目 Pass 確認・UI は `specs/evaluation-rubric.md` 採点） |
| 「大規模リファクタ」「複数領域にまたがる変更」 | **オーケストレーター・ワーカー** | メインがオーケストレーター：計画をファイルに保存→タスク分解→ワーカー（`serena-expert`/`general-purpose`）に領域別委任→統合・検証 |
| 迷ったら | **壁打ちで開始** | 行き詰まり・規模超過が**実測**されたら昇格（推測で複雑化しない） |

## ツール割り当て（最小権限）

| エージェント | 役割 | 持たせるツール | 持たせない |
|---|---|---|---|
| メイン（壁打ち/オーケストレーター） | 対話・計画・統合・検証 | 全ツール | — |
| `code/security/performance-reviewer` | 評価（投票） | Read/Grep/Glob/Bash＋Write（**agent-memory 限定はプロンプト側の運用**・ツール権限では未強制） | 対象コードの Edit（レビューは指摘のみ） |
| `serena-expert` | 実装ワーカー | 全ツール（serena MCP でシンボル単位編集） | DB 書き込み系（PreToolUse フックが強制） |
| `Explore` / `general-purpose`（CLI 組み込み） | 調査ワーカー | 読み取り・検索系中心 | 書き込み（調査に不要） |
| Evaluator（検収・**専用定義なし＝都度プロンプトで構成**） | contract/rubric 判定 | Read/Grep/Bash（`npm run verify`・`npm test`）＋必要なら Playwright MCP | テストファイルの書き換え（抜け道封じ） |

> さらに重い並列オーケストレーション（Workflow 機能）は**ユーザーの明示オプトインがあるときだけ**使う（「ワークフローで」「ultracode」等）。既定は Agent ツールの並列呼び出しで足りる。

## 計画のメモリ保存（委任前の必須手順）

1. **機能開発**：`docs/0NN_*.md` チケット（Todo チェックボックス）＋必要なら `specs/sprint-contract.md` — これが正典の計画。
2. **セッション内の分解作業**：TaskCreate（タスクリスト）で進捗を可視化。大きい計画はスクラッチパッドに `plan.md` を書き、各ワーカーへの指示にファイルパスを渡す。
3. **ワーカーの出力**：結論の要約をメインへ返し、根拠・詳細が大きい場合はファイル（docs/ または scratchpad）に書かせてパスを報告させる。
4. **中断への備え**：長時間作業は完了分・未完了分・次アクションをチケットに随時反映（構造化ハンドオフの簡易版）。

## 品質ゲートとの接続

- どのパターンでも完了主張の前に **`npm run verify`（lint→typecheck→test→build）** を通し出力を提示する（AGENTS.md §4）。
- push は必ず **`/push-review`**（ファンアウト＋投票）経由 — パターンの重複適用で OK（実装をパイプラインで作り、push はファンアウトで守る）。
- サブエージェントへの指示には **agent-memory に回避手順を書かない**旨を含める（instruction poisoning 防止・#020 で確立）。

## アンチパターン（やらない）

- 簡単な質問への多段エージェント起動（コスト浪費・伝言ゲームによる劣化）。
- 計画をファイル化せずに長い委任を開始（文脈切れで迷子になる）。
- レビュアーに Edit を持たせる／実装ワーカーに検収させる（役割の混線＝自己評価バイアスの再発）。
- 「並列にできそう」だけで分割（依存があるタスクの並列化は統合コストで逆に遅くなる）。
