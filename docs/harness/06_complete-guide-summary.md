## 1. このガイドの結論

AIエージェント時代のエンジニアは、コードを直接書くだけでなく、AIが安定して成果を出せる環境を設計・制御・評価する「ハーネス設計者」になる。

AIには、コード生成・大量ファイルの横断理解・定型処理のような強みがある一方、長時間の一貫性、自己評価、曖昧な要件の解釈には弱さがある。この凸凹の大きい「スパイキーな知性」に対し、弱点には構造を与え、強みは安全に委任できるよう境界と検証を整えるのがハーネス設計である。

最も重要な進め方は、強いモデルと小さなプロンプトから始め、実際の失敗を観察し、効果を測れる補助だけを追加すること。ハーネスの各部品は「モデルが単体ではできないこと」についての仮説であり、モデルの進化に合わせて不要なものを外す必要もある。

## 2. コンテキストエンジニアリングの4戦略

コンテキストウィンドウは有限のワーキングメモリである。情報を多く入れるほど良いわけではなく、高シグナルな情報を必要な時に渡すことが品質を左右する。

| 戦略 | 目的 | 代表的な実装 |
|---|---|---|
| **Write** | 知識や進捗を外部記憶へ書き出し、セッションをまたいで保持する | `CLAUDE.md`、進捗ファイル、TODO、メモリ |
| **Select** | 必要な情報だけを必要な時に取得する | Rules、Skills、MCP、ファイル検索 |
| **Compress** | 重要な判断を残し、履歴やツール結果の冗長さを削る | 会話要約、古いツール結果の除去 |
| **Isolate** | 重い調査や独立作業を別コンテキストへ分離する | サブエージェント、並列レビュー |

4戦略は単独で使うものではない。永続知識をWriteし、タスクに必要なものだけSelectし、長くなった履歴をCompressし、独立作業をIsolateすることで、メインのコンテキストを健全に保つ。

## 3. Claude Codeの6つの制御インターフェース

| インターフェース | 役割 | 主な戦略・性質 |
|---|---|---|
| `CLAUDE.md` | プロジェクトの構造、コマンド、規約、禁止事項を常時共有する取扱説明書 | Write |
| Rules | 対象ファイルのパターンに応じて固有ルールを注入する | Select |
| Hooks | ツール実行前後に検証や後処理を差し込む | 決定論的制御 |
| Skills | 繰り返し使うタスク固有の手順をオンデマンドで読み込む | Select |
| サブエージェント | 調査・実装・評価を独立した文脈へ分離する | Isolate |
| MCPサーバー | 外部サービスとの操作を構造化されたツールとして提供する | Select / ACI |

`CLAUDE.md` には、AIがコードから推測できない情報を具体的に書き、可能なら理由も添える。すべてを常時読み込ませず、ファイル固有の規約はRules、作業手順はSkills、外部操作はMCPへ分ける。

## 4. Hooks：お願いを強制へ変える

自然言語の規約は確率的であり、常に守られる保証はない。失敗が許されない操作はHooksで決定論的に制御する。

- **PreToolUse**：実行前に入力を検査し、危険な削除、強制push、本番DBの破壊的操作などをブロックする。
- **PostToolUse**：編集後のlint、format、型検査など、反復可能な品質確認を自動化する。
- **Notification**：長時間タスクの完了や承認待ちを人間へ通知する。

Hookは、正常時には処理を続行し、拒否時には明確な理由と安全な代替案を返すよう設計する。柔軟な判断が必要な規約は文章に残し、絶対条件だけをHookへ移す。

## 5. エージェント設計の基本パターン

### 5.1 ルーティング

入力や対象領域を分類し、専門のプロンプト・ルール・エージェントへ振り分ける。Claude CodeのRulesは、ファイルパスをルーターとして使う例である。

### 5.2 ACI（Agent-Computer Interface）

人間向けUIと同様に、AI向けツールにも使いやすさが必要である。ツール名、引数、返却形式、エラー内容が曖昧だと、モデル能力が高くても成果が落ちる。

設計上の要点は次のとおり。

- 書き込み前に考えられる余地を与える。
- JSONやMarkdownなど自然で標準的な形式を使う。
- 行番号や内部IDなど不要な操作負荷を減らす。
- 引数名とツール名を具体的にし、初見でも用途が分かるようにする。

### 5.3 投票

同じ対象を複数の独立した視点で評価し、複数の評価者が一致した問題を高確度として扱う。セキュリティ、性能、保守性など、観点を分けると重複だけでなく補完も得られる。

## 6. Generator–Evaluator：生成と評価を分ける

生成者は、自分が作ったものの前提や文脈を引きずるため、客観的な自己評価が難しい。成果物を作るGeneratorと、基準に照らして検証するEvaluatorを別コンテキストに分離する。

実践上は、作業前に次を合意する。

- **スプリントコントラクト**：何ができれば完了かを二値判定できる形で定義する。
- **評価ルーブリック**：品質の程度を段階評価する基準を定義する。
- **検証方法**：テスト、Playwright、API確認など、証拠の取り方を定義する。

コードレビューだけでなく、実際にアプリを操作するライブ検証を組み込む。反復は無制限にせず、品質基準を満たした時点、または改善が逓減した時点で止める。

## 7. マルチエージェント設計

単一エージェントには、コンテキスト容量、専門性の希釈、処理時間という限界がある。タスクの依存関係に応じて3パターンを使い分ける。

| パターン | 向くタスク | 特徴 |
|---|---|---|
| オーケストレーター・ワーカー | 分解方法が途中で変わる複雑な仕事 | 中央のエージェントが計画・委任・統合する |
| シーケンシャルパイプライン | 工程間に明確な前後依存がある仕事 | Planner → Generator → Evaluator など順番に渡す |
| ファンアウト・ギャザー | 独立して並列化できる調査・レビュー | 同時実行した結果を最後に統合する |

簡単な仕事まで複数エージェント化しない。並列化できる独立性、評価の独立性、コンテキスト分離の必要性がある時だけ使う。各エージェントには必要最小限のツールと、明確な目的・出力形式・成功条件を渡す。

## 8. 長時間エージェントの管理

長いセッションでは、文脈の劣化、未検証情報の蓄積、早すぎる完了宣言が起きやすい。対策の中心は、状態を会話の外へ出すことである。

- 完了、未完了、重要判断、次の作業を進捗ファイルへ記録する。
- 機能一覧と検証手順を構造化し、合否だけを更新可能にする。
- テスト項目自体をエージェントが消して成功扱いにできないよう保護する。
- セッションを定期的にリセットし、構造化された引き継ぎ文書から再開する。
- lint・テストなどの外部検証を使い、検証済み事実だけを永続化する。

会話の自動要約だけに依存すると、何が失われたかを判断しにくい。重要な状態は、人間が読んでも次の担当者が迷わない引き継ぎとして明示する。

## 9. エージェント向けツール設計

ツールは、エージェントが環境に対して何をできるかを決めるアフォーダンスである。APIをそのまま大量に公開するより、タスクに必要な少数の操作へ整理する方が誤選択を減らせる。

### 設計原則

- なくても完了できるツールは追加しない。まず3〜5個程度に絞る。
- API単位でなく、利用者のタスク単位で操作をまとめる。
- 名前は `{service}_{resource}_{action}` のように一貫させる。
- 内部IDやMIMEタイプなど、判断に不要な情報を返さない。
- 詳細度を選べるようにし、通常は簡潔な結果を返す。
- エラーには原因、修正例、次に試す候補を含め、自律回復を助ける。

ツールは、説明文を整えたプロトタイプを作り、現実的な複数ステップのシナリオで試し、実行ログを読んで改善する。この考え方はMCPだけでなく、SkillsやRules、開発コマンドの説明にも適用できる。

## 10. 検証ループの体系化

品質を上げる本体は特定のテスト手法ではなく、生成 → 検証 → フィードバック → 改善 → 再検証というループである。

| 戦略 | 向く対象 | 例 |
|---|---|---|
| ルールベース | 正誤を決定的に判定できるもの | lint、型検査、単体テスト、ビルド |
| ビジュアル | UIやレイアウトなど視覚的品質 | スクリーンショット比較、マルチモーダル評価 |
| LLM-as-Judge | トーン、可読性、創造性など主観的品質 | 独立コンテキストの評価者、Few-Shot採点 |

最初は高速で再現性の高いルールベース検証を置く。そこでは表現できない基準がある場合に限り、ビジュアル評価やLLM評価を重ねる。各層の盲点が一直線に並ばないよう、異なる方式を組み合わせる。

## 11. 評価ハーネス

エージェントハーネスが仕事を実行する仕組みであるのに対し、評価ハーネスはその性能を継続的に計測する仕組みである。

### 5つの構成要素

1. **Tasks**：参照解答や成功条件を持つ評価課題。
2. **Trials**：非決定性を見るための複数回試行。
3. **Transcripts**：プロンプト、ツール利用、途中判断を含む行動ログ。
4. **Graders**：成果や過程を採点する関数・モデル・人間。
5. **Outcomes**：成功率、コスト、時間などの集計結果。

### Graderの使い分け

- **Code-based**：速く決定的。機械判定できる項目の第一選択。
- **Model-based**：曖昧な品質を評価できる。具体例で校正し、スコアドリフトを監視する。
- **Human**：最終的な正解基準であり、他のGraderを校正する。

新しい能力の限界を探るCapability Evalと、既存能力の退行を防ぐRegression Evalは分けて扱う。複数試行では、一度でも成功する可能性を見る `pass@k` と、毎回成功できる信頼性を見る `pass^k` を目的に応じて使う。

最初から巨大なベンチマークを作らず、最近のバグ、頻出要求、エッジケース、難題を組み合わせた20件程度から開始する。Grader自体もトランスクリプトと人間判断で検証する。

## 12. ケーススタディから得られる教訓

### フルスタック開発

Planner、Generator、Evaluatorを分離し、作業前のコントラクト、実装、ライブ検証を順につなぐ。単一エージェントより時間とコストは増えても、利用可能な品質へ到達する確率が高まる。最適化すべきなのは単発の安さではなく、正しく動く成果までの総コストである。

### コンテンツ生成

Generatorの出力を複数観点で並列評価し、フィードバックを次の反復へ渡す。最大反復数と合格基準を先に定め、評価結果をファイルへ残す。

### リサーチ

単一の検索で終わらせず、途中結果から検索方針を更新する多段探索と、独立した領域の並列調査を組み合わせる。オーケストレーターは情報を集めるだけでなく、探索の不足や重複を判断する。

## 13. 実践ロードマップ

### 今日から始める

1. `CLAUDE.md` をプロジェクトの取扱説明書として育てる。
2. 成果物を別セッションまたは別エージェントに評価させる。
3. 「AIがXを単体ではできない」という仮説を一つ選び、最小の補助を入れて効果を測る。

### 導入順序

1. 最小のプロンプトと強いモデルでベースラインを測る。
2. lint・型検査・テストなど決定論的な検証ゲートを置く。
3. 失敗や判断を外部ファイルへ記録する。
4. 必要な情報だけをRules・Skills・MCPで選択的に渡す。
5. 不可逆な事故だけをHooksで防ぐ。
6. 自己評価が問題になる作業でGeneratorとEvaluatorを分ける。
7. 独立性や分業効果が確認できる場合だけマルチエージェント化する。
8. 繰り返し評価したくなった時点で、小さな評価ハーネスを作る。
9. 定期的に構成を再評価し、効果のない部品を削る。

## 14. 設計チェックリスト

- [ ] AIの強みと弱みを、対象タスクについて具体化したか。
- [ ] 成功条件と検証方法を作業前に定義したか。
- [ ] 常時必要な情報と、必要時だけ読む情報を分けたか。
- [ ] 重要な進捗・判断・未解決事項を外部へ永続化したか。
- [ ] 失敗が許されない操作だけを決定論的にブロックしたか。
- [ ] ツールは少数で、名前・引数・エラーが自己説明的か。
- [ ] 生成者と評価者の文脈を必要に応じて分離したか。
- [ ] ルールベースの検証を最初の品質層として置いたか。
- [ ] 並列化するタスクは本当に独立しているか。
- [ ] ハーネス追加の効果を計測できるか。
- [ ] モデル進化後も必要な構造かを定期的に見直しているか。
