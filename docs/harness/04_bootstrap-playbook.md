# プロジェクト起ち上げプレイブック（AI エージェント開発の始め方）

> 新しいソフト開発プロジェクトを AI エージェント（Claude Code / Codex）と始めるときの手順書。
> 本リポジトリで実証したハーネス構造（[01_principles.md](./01_principles.md)・[02_maturity.md](./02_maturity.md)）を、次のプロジェクトへ移植するための資産。

## 大原則（先に読む）

> **最初に入れるのは「安全」と「仕様」だけ。残りのハーネスは開発の失敗から育てる。**

- 教材・Anthropic の一貫した推奨：**シンプルから始め、複雑さは実測で効果が証明された場合のみ追加**する。
- ハーネスの各部品は「モデルが単体でできないこと」への**仮説**。仮説が生まれる前に部品を作り込むのは過剰設計（YAGNI）。
- 例外は2つだけ先に入れる価値がある：
  1. **安全（不可逆な事故の防止）** — ガードレールは事故が起きてからでは遅い。
  2. **仕様（spec-first の土台）** — docs が無いとエージェントが勝手に仕様を発明する。

```
Phase 0        Phase 1        Phase 2         Phase 3          Phase 4
安全の最小セット → 仕様を書く → PoC 開発ループ → issue 駆動改善 → ハーネスを育てる
（1日）         （人間+AI）    （チケット単位）   （1 issue=1 PR）  （失敗→構造化）
                                    └──────── 繰り返し ────────┘
```

## Phase 0 — 安全の最小セット（初日に・開発前）

リポジトリ初期化と同時に作る。**ここまでが「構築してから開発」の範囲**（それ以上は作り込まない）。

| 成果物 | 内容 | 本リポジトリの雛形 |
|---|---|---|
| `.gitignore` | `.env*`・`.mcp.json`・ビルド成果物・`*.tsbuildinfo` 等 | `/.gitignore` |
| `AGENTS.md` | **正典（ツール非依存）**：安全ルール（変更禁止ゾーン・spec-first・最小差分・検証義務・Git 安全則・シークレット非開示・報告テンプレ）＋レビュー基準の骨子 | `/AGENTS.md` |
| `CLAUDE.md` | **10行から**：`@AGENTS.md` ＋スタック＋コマンド＋最小の規約。育てる前提で薄く | `/CLAUDE.md` |
| `.claude/settings.json` | チーム共有 hooks：**PreToolUse ガードレール**（破滅的 rm・force push・一括 add・.env ステージ・DB 書き込み）＋ Notification 音 | `/.claude/settings.json` |
| `.claude/hooks/` | `validate-bash.sh`・`validate-supabase-write.sh`（相当）・`notify.sh` をコピーして対象を調整 | `/.claude/hooks/` |
| `.mcp.json` | **必要最小限の MCP のみ**（3〜5。多いほど誤選択が増える＝ACI 原則）。トークンを含むため gitignore | `/.mcp.json`（非追跡） |
| 検証ゲート | `npm run verify` 相当（lint→typecheck→build or test）＋ CI（PR/main push で必須化） | `/package.json`・`/.github/workflows/ci.yml` |

**まだ作らないもの（仮説が生まれてから）**：多数の skills、サブエージェント群、評価ハーネス、細かい rules。

## Phase 1 — 仕様を書く（人間 + AI で・コードより先）

`docs/` に**チケット制の索引**と**設計ドキュメント**を置く。エージェントは「docs に無い変更は着手前に停止」（spec-first）。

```
docs/
├── 000_index.md          # チケット一覧・進捗（完了/全体・ステータス）
├── specs/                # 設計ドキュメント（開発前に人間+AIで書く）
│   ├── 01_overview.md    #   基本設計：目的・ユーザー種別・スコープ（外も明記）
│   ├── 02_architecture.md#   アーキテクチャ：スタック・構成図・境界
│   ├── 03_db.md          #   DB設計：スキーマ・RLS/認可・マイグレーション方針
│   ├── 04_design.md      #   デザイン：UI方針・デザインシステム/トークン
│   ├── 05_api.md         #   詳細設計：ルート構成・Server Action/API の形
│   └── 06_test.md        #   テスト方針：検証ゲート・手動確認手順・ロール別確認
├── 0NN_*.md              # 機能チケット（Todo チェックボックス付き）
└── harness/              # 本ナレッジ（コピーして持っていく）
```

- 書き方のコツ：**MVP スコープ外を明記**（エージェントの勝手な実装を防ぐ）／「なぜ」を添える（AI の判断力が上がる）。
- 仕様は AI とブレインストーミングして書き、**人間が確定**させる。

## Phase 2 — PoC 開発ループ（チケット単位）

1. チケットの Todo を読む → feature ブランチ（`<type>/<kebab-case>`）
2. 実装（最小差分・既存パターン踏襲）
3. **検証ゲートを必ず通す**（verify）＋ UI は目視、認証系は 3 ロール確認
4. チケットの `- [ ]`→`- [x]` と索引を**即時更新**
5. 小さくコミット（1コミット1目的）→ PR（1 PR 1 論理変更）

この段階のレビューは人間＋CI で十分。**3レビュアー並列（投票パターン）はコード量が増えて価値が出てから**導入する（本リポジトリでは #9 で導入した）。

## Phase 3 — issue 駆動の改善ループ（PoC 後）

1. PoC を触って改善点を洗い出し、**1件ずつ GitHub issue に発行**（`gh issue create`）
2. 1 issue = 1 ブランチ = 1 PR で改善（`closes #N` でクローズ）
3. マージのたびにローカル/リモートを同期

## Phase 4 — ハーネスを育てる（Phase 2〜3 と並走）

**失敗が起きたら、その失敗を構造に変換する**。これが「当該プロジェクト用の AI を育てる」の実体。

| 起きたこと | 変換先 | 判断基準 |
|---|---|---|
| エージェントが規約を破った（確率的に） | `CLAUDE.md`/`AGENTS.md` に理由付きで追記 | まず「お願い」で足りるか試す |
| 特定ファイル種別でだけ必要な規約が増えた | `.claude/rules/*`（`paths:` glob）に分離 | 常時読み込みはしない（Select 戦略） |
| **絶対にやってはいけない操作**をやりかけた | **PreToolUse フックで `exit 2` ブロック** | 失敗が許されない＝決定論的に強制 |
| 編集のたびに同じチェックを繰り返している | PostToolUse フック（lint-on-save 等） | 決定論的にできるものは自動化 |
| 同じ手順を何度も指示している | `.claude/skills/`（スラッシュコマンド化） | 3回繰り返したら skill 化 |
| レビュー観点が固まってきた | サブエージェント（reviewer）＋投票パターン | コード量・リスクが増えてから |
| ハーネス変更の効果が判断できない | 評価ハーネス（20タスク＋pass@k） | 部品が増えて退行が怖くなってから |

- 変更のたびに `02_maturity.md` 方式で**成熟度を再採点**し、次の一手を決める。
- **モデルが進化したら不要になった部品を削る**（ハーネスはシンプルに保つ）。

## Phase 5 — デュアルツール運用（Claude Code × Codex）

- **`AGENTS.md` が正典**：ツール非依存の規範はここに集約（Claude Code も Codex も読む）。`CLAUDE.md`／`.claude/` は Claude Code 固有の配線に留める。
- 役割分担の例：
  - **Claude Code**：実装・チケット運用・`/push-review`・ハーネス実行
  - **Codex**：独立した分析・セカンドオピニオン（PR レビュー等）
- これは **Generator-Evaluator の強化形**：別ベンダーのモデルを評価者に使うと、自己評価バイアスの分離がさらに効く。
- 注意：どちらのツールで作業しても「spec-first・最小差分・検証ゲート」は同一（規範が AGENTS.md にあるため）。
