## 0. コアテーゼ

エンジニアの役割は **コードを書く側 → AI を設計・制御・評価する「ハーネス設計者」** へ移行する。
同じモデルでも **ハーネス（制御構造）の有無で成果が劇的に変わる**。AI は **スパイキーな知性**（得意と苦手の凸凹が激しい）を持つため、

> **ハーネス設計者の仕事 = AI の「得意」を活かし「苦手」を補う環境を設計すること。**

### 🧭 本プロジェクトの設計哲学（2つの指針）

> **① AI の凹みに構造を、でっぱりは安心して任せられるように。**
> スパイキーな知性の「凹み（苦手）」— 長時間の一貫性・自己評価・曖昧な要件解釈 — には**構造（ルール・フック・進捗ファイル・評価者）で足場を組む**。
> 「でっぱり（得意）」— コード生成・大量ファイルの横断理解・定型処理 — は**安心して委任できる**ように、周辺の検証と境界だけを固める。
> ＝ ハーネス設計とは「どこに構造を足し、どこは任せるか」の線引きである。

> **② モデルが進化しても、設計したハーネス構造は資産として永続する。**
> モデル改善で個々の部品は不要になりうる（新しいモデルほど少ない足場で同等以上）。だが **W/S/C/I や「生成と評価の分離」「決定論的ガードレール」といった設計原則そのものはモデル非依存のメタスキル**であり、部品を組み替えながら価値を持ち続ける。
> だからハーネスは「書き捨て」ではなく **蓄積・洗練していく資産**として `docs/` に永続化する（＝Write戦略）。定期的に前提を見直し、不要な部品は取り除いてシンプルに保つ。

| AI が得意 | AI が苦手 |
|---|---|
| パターンに基づくコード生成 | 長時間の一貫性維持 |
| 大量ファイルの横断的理解 | 自分の出力の客観的評価 |
| 定型タスクの高速処理 | 曖昧な要件の解釈 |

**貫く原則**：最も強力なモデルで最小限のプロンプトから始め、失敗を観察して段階的にコンテキスト／複雑さを足す。**複雑さは実測で効果が証明された場合のみ追加する。**

## 1. コンテキストエンジニアリング 4戦略（W・S・C・I）

コンテキストウィンドウ＝有限のワーキングメモリ。詰め込みすぎると注意が分散し精度が下がる。**最小限の高シグナルなトークンで最大の成果**を狙う。

| 戦略 | 意味 | Claude Code での実装 | 本プロジェクトの対応物 |
|---|---|---|---|
| **Write** | 外部記憶へ知識を永続化しセッションを超えて引き継ぐ | CLAUDE.md / 進捗ファイル / メモリ | `CLAUDE.md`・`AGENTS.md`・`docs/` チケット・`.serena/memories/` |
| **Select** | 必要な情報だけJITで取り込む（プログレッシブ・ディスクロージャー） | Rules / Skills / MCP | `.claude/rules/backend\|frontend/patterns.md`・Skills |
| **Compress** | 要約・トリミングで窓を最大活用（重要判断は残し冗長は捨てる） | コンパクション / ツール結果クリアリング | ハーネス自動（＋長時間対策は §8） |
| **Isolate** | サブエージェントで文脈を分離し並列処理。結果は要約(1–2kトークン)で返す | サブエージェント | `code/security/performance-reviewer` の3並列 |

## 2. Claude Code の6つの制御インターフェース

| IF | 戦略 | 使いどころ | 読み込みタイミング |
|---|---|---|---|
| **CLAUDE.md** | Write | プロジェクト全体の規約・知識（取扱説明書） | 常時 |
| **Rules** | Select | ファイル種別ごとの指示（フロントマターの glob で連動） | パターンマッチ時 |
| **Hooks** | （制御） | ツール実行の前後に検証を差し込むミドルウェア | ツール呼び出し時 |
| **Skills** | Select | タスク固有の手順書（レシピ）。`/command` で明示呼び出し | 明示呼び出し時 |
| **サブエージェント** | Isolate | 並列調査・大規模分析。独立コンテキストで文脈保護 | タスク委任時 |
| **MCP サーバー** | Select | 外部システム連携を型付きインターフェースで構造化 | ツール呼び出し時 |

**CLAUDE.md の書き方のコツ**：「Claude が推測できない情報」を「理由付きで」具体的に書く（例：「テストを書く」→「全 public メソッドにユニットテストを書く」）。定期的に更新し、不要ルールは削除。

## 3. Hooks — 確率的な「お願い」を決定論的な「強制」に変える

- **CLAUDE.md = お願い（確率的）**：高確率で従うが100%ではない。
- **Hooks = 強制（決定論的）**：`exit 2` を返せば **100% 実行されない**。

**「失敗が許されない制御」には Hooks を使う。柔軟な判断が必要なら CLAUDE.md。**

### インターフェース仕様
| 要素 | 動作 |
|---|---|
| `stdin` | ツール名・引数の JSON（`jq -r '.tool_input.command'` で抽出） |
| `exit 0` | 許可（実行続行） |
| `exit 2` | ブロック（決定論的に阻止） |
| `stdout` | Claude のコンテキストへ（代替案を検討させる） |
| `stderr` | ユーザーの画面へ直接表示 |

### 3タイプ
- **PreToolUse**：実行前に検証。危険な操作を `exit 2` で確実にブロック（例：`rm -rf`、本番DBへの破壊的操作）。
- **PostToolUse**：実行後に後処理。lint / フォーマットを自動実行（`async: true` で作業を止めない）。品質の自動ゲート。
- **Notification**：長時間タスク完了・承認待ちの通知（デスクトップ通知 / Slack Webhook / ターミナルのベル音）。

## 4. エージェント設計パターン（Anthropic: Building Effective Agents）

- **ルーティング**：入力を分類し専門ハンドラへ振り分ける。関心の分離。→ Claude Code の **Rules はファイルパスによるルーティング**。
- **ACI 設計（Agent-Computer Interface）**：人間向け UI/UX と同じく、**AI 向けにツールの使い勝手を設計**する。**プロンプト最適化よりツール最適化の方が成果が大きい**（Anthropic の SWE-bench 実績）。
  - 4原則：①思考の余裕（書き込み前に計画）②自然な形式（標準 JSON/Markdown）③オーバーヘッド排除（行番号でなく内容で指定）④明確な命名（`file`→`absolute_file_path`）。
  - 基準：**「初めて使うジュニア開発者でも迷わないか」**。
- **投票パターン**：同一タスクを複数の独立エージェントで実行し合意形成。**2つ以上が指摘した問題＝高確度**として優先。→ 本プロジェクトの3視点レビュー（security/performance/保守性）はこの実装。

## 5. Generator-Evaluator — 生成と評価の分離

**自己評価は構造的に信頼できない**：作った本人に評価させると自信を持って自作を称賛する（生成時の文脈が評価をバイアスする）。

- **GAN 的に生成者と評価者を分離**。独立した評価者を「懐疑的」にチューニングする方が、生成者に自己批判させるより遥かに簡単。
- **グレーダブル・クライテリア**：曖昧な指示を「低スコア/高スコアの具体状態」に変換し `evaluation-rubric.md` に保存 → 評価者が参照。
- **スプリントコントラクト**：実装前に Generator と Evaluator が完了基準を合意（`sprint-contract.md`）。過度な仕様書は不要、**検証可能な完了条件**に焦点。
- **ライブ検証**：コードレビューでなく **実際にアプリを操作して**評価（Playwright で UI 操作・API・DB 状態確認）。
- **ファイルの単一責任**：`sprint-contract.md`（何を作るか＝二値判定）と `evaluation-rubric.md`（どの程度良いか＝段階評価）を分ける。
- **反復の目安**：フロントデザイン5–15回／フルスタック3–5スプリント。最初の2–3回で最大改善（収穫逓減）。品質基準を満たす**最小限の反復**で止める。

## 6. マルチエージェント設計

単一エージェントの限界＝①コンテキスト容量 ②専門性の希釈 ③処理時間。**トークン使用量だけで性能の80%の分散を説明できる**（＝コンテキストの質と量が成果を直接決める）。

| パターン | タスク関係 | 速度 | 典型例 |
|---|---|---|---|
| オーケストレーター・ワーカー | 相互依存あり（動的分解） | 中 | 大規模リファクタリング |
| シーケンシャルパイプライン | 前後依存（工程固定） | 遅 | コンテンツ生成（Planner→Generator→Evaluator） |
| ファンアウト・ギャザー | 独立（並列分割） | 最速（最大90%時短） | コードレビュー・多角分析 |

実装のコツ：**クエリの複雑さでスケール**（簡単な質問に大量エージェントを使わない）／**ツールを厳選**／**計画を外部ファイルに保存**。「プロンプトエンジニアリングが主要なレバー」。

## 7. 長時間エージェントの管理

- **コンテキスト不安**：窓が埋まると（〜75%）モデルが残量を「察して」早期に手を抜き、楽観的な完了宣言をする。
- **コンパクションより全リセット＋構造化ハンドオフ**：要約は「何が失われたか分からない」リスクがある。コンテキストを完全クリアし、引き継ぎ文書（完了/未完了タスク・重要判断・次アクション）で再開。「交代勤務の完璧な引き継ぎノート」。
- **進捗ファイル**：エージェント自身が各タスク完了時に更新（人間が書くのではない）。→ 本プロジェクトの `docs/` チケット運用。
- **フィーチャーリストのロック**：`feature_list.json` は `passes` フィールドの変更のみ許可。**テスト項目の削除・編集は禁止**（エージェントがテストを消して「全合格」にするのを防ぐ）。
- **コンテキスト毒性（幻覚の残留）対策**：定期的な全リセット／外部検証（lint・テスト）で幻覚を検出／主張をツール結果で裏付け／検証済み事実だけを外部ファイルに記録。

## 8. エージェント向けツール設計（Anthropic: Writing Tools for Agents）

- **プロンプトよりツール設計が重要**。ツールはエージェントが「何ができるか」を知覚するアフォーダンス。
- **選択的実装**：全 API をラップしない勇気。**3〜5ツールに絞る**（Vercel v0 はツールを80%削減して成果向上）。判断基準＝「このツールが無くてもタスクを完了できるか？ Yes なら不要」。タスク指向で統合（`list_*`→`search_*`）。
- **コンテキスト効率**：UUID・MIMEタイプ・内部IDを除外、人間可読に変換、アクション関連情報のみ返す（`format: concise|detailed`）。
- **命名**：`{service}_{resource}_{action}` の3層（例 `github_issues_search`）。
- **エラー設計**：`{error, message, example, suggestions}` で**自律回復**を促す（「ジュニア開発者にドキュメントを書くように」）。
- **3フェーズ改善**：①LLMフレンドリーな説明付きでプロトタイプ ②現実的な複数ツール呼び出しシナリオで評価 ③**トランスクリプト（実行ログ）を読んで**行動を観察・改善。

> CLAUDE.md のコマンド記述にも同原則が効く：`npm run build` → `npm run build — 本番ビルドを生成。型チェックも兼ねる` のように**理由と効果を添える**。

## 9. 検証ループの体系化

**フィードバックループという構造そのもの**が品質を2〜3倍改善する（特定の検証手法ではなく）。生成→検証→FB→改善→再検証。

| 戦略 | 得意な評価対象 | タイミング | 本プロジェクト |
|---|---|---|---|
| **ルールベース** | コード品質・型・テスト（決定論的・高速・曖昧さゼロ） | 常にベースライン | `npm run verify`（lint→typecheck→build）＋ CI。PostToolUse フックで自動ゲート化も可 |
| **ビジュアル** | UI・レイアウト・デザイン（スクショ×マルチモーダル） | 視覚的出力がある場合 | Playwright MCP あり。material-design skill が一部活用 |
| **LLM-as-Judge** | トーン・創造性・可読性など主観的品質 | 主観基準が必要な場合 | reviewers が近い役割 |

原則：**まずルールベースで始め、ルールで表現できない基準がある時だけ他戦略を足す。**

## 10. 評価ハーネス設計（Anthropic: Demystifying Evals）

**エージェントハーネス（実行）と評価ハーネス（計測）は別物。**

- **5構成要素**：Tasks（参照解答付きの問題）/ Trials（複数回試行）/ Transcripts（全行動ログ）/ Graders（採点関数）/ Outcomes（集計スコア）。
- **3種の Grader**：Code-based（高速・決定的）→ Model-based（曖昧な基準、Few-Shotでキャリブレーションしスコアドリフト防止）→ Human（ゴールド標準・校正用）。
- **2種の評価**：Capability Eval（限界を探る、合格率30–50%が健全）／ Regression Eval（退行防止、≒100%であるべき）。
- **非決定性の計測**：`pass@k`（k回中1回でも成功＝楽観的、バッチ向き）／`pass^k`（k回全成功＝悲観的、対話型向き）。
- **Swiss Cheese Model**：各手法に盲点がある → 多層で穴が一直線に並ばないようにする。
- **始め方**：20タスク（最近のバグ5–7・よくある要求5–7・エッジケース5–7・難題2–3）から。「評価インフラへの投資は複利のリターン」。

## 11. 実践ケースの教訓

- **フルスタック**：Planner/Generator/Evaluator の3構成。単独 $9・20分（破綻）vs ハーネス $200・6時間（実用品質）。→ **低コストで壊れたものより、適正コストで動くもの。**
- **コンテンツ生成**：並列評価＋最大3反復＋各回の評価をファイル記録。
- **リサーチ**：動的多段検索＋並列で単一比90.2%性能向上。

> **ハーネス設計の本質**：「ハーネスの各部品は、モデルが単体でできないことについての**仮説**の集積。その仮説はストレステストする価値がある」。
> モデルは進化する → 前提が今も正しいか定期的に見直し、**不要になった部品は取り除いてシンプルにする**。設計原則（W/S/C/I）自体はモデル非依存の**メタスキル**。

## 12. 明日から始める3アクション（本プロジェクト版）

1. **CLAUDE.md を育てる** — 既にある。新しい知見を追記し、不要ルールを削除し続ける。
2. **Generator-Evaluator を試す** — 生成後、別セッション／別エージェントで評価し自己評価との差を体感する（reviewers 活用）。
3. **ハーネスの仮説を検証する** — 「AI が X を自力でできないはず」と仮説を立て、補助（Rule/Hook/Skill）を入れて検証。正しければ組み込み、間違いなら取り除く。
